# montagewright

丟一個資料夾的毛片進去，出來一支剪好的片，還有一份說明每個決定是怎麼來的報表。

```bash
montagewright render RUSHES/ --brief BRIEF.md --music TRACK.mp3 \
  --aspect 9:16 --review --output CUT/

montagewright transcribe VIDEO.mp4        # 只要字幕，不重剪
montagewright-web                         # 同一件事，網頁上看得到過程
```

---

如果有人想研究 AI 剪輯但沒什麼頭緒，這裡是我把雲端跟地端接起來的做法。

整套的判斷只有一句：**看得懂才答得出來的問題交給模型，要量才知道的問題交給程式。** 下面兩段是同一個問題解兩次 —— Gemini 負責找出那是什麼，本機負責算出它在哪、在第幾秒。

## 【影像】

先用 ffmpeg 把毛片壓成 proxy（640px / 15fps），讓 Gemini 整支連聲音看完，寫成一張 Clip Card：拍到什麼、可以框住的東西在哪、什麼動作發生在第幾秒、攝影機自己有沒有在動、聲音算不算內容。卡片存在本機，用檔案內容的 hash 命名。

**卡片刻意不看 brief。** 看著 brief 寫的卡片換一個 brief 就得重寫；看著素材寫的卡片，素材沒變就一直有效。同一批素材要剪成別的主題，不用再讓 Gemini 重看全部毛片 —— 實測 74 支第一次 $1.43，第二支片 $0.55。

要把橫式毛片重新構圖成 9:16、或讓畫面持續跟著人物移動，還得知道物件在**每個影格**的位置。先用 [Gemini 的物件偵測](https://ai.google.dev/gemini-api/docs/image-understanding)從那顆抽五張靜幀，問「左邊那台深色手機」在哪 —— 這是語意問題不是幾何問題，它做得很好。（陷阱：回傳的是它自己的 0..1000 座標系，換算要在收到時做，靠 prompt 拜託沒有用。）

靜幀只代表單一時點，抽樣點之間發生什麼沒人知道。所以接著用 **SAM 2.1** 把那個框當種子往前後傳播，追出每一幀。追丟的幀丟掉並回報比例 —— 曾經九幀只追到兩幀，剩下那一幀變成整段軌跡，裁切框最後停在一隻手上。**會動的主體才追**，靜止的直接用卡片裡的框。

裁切路徑寫成 ffmpeg 的逐幀運算式（smoothstep 緩入緩出），所以運鏡是連續的不是跳接。用過的路徑跟成片一起存下來，事後可以把框畫回原素材，確認它真的有瞄在該瞄的地方。

## 【音訊】

受 Palmier Pro 用 Apple SpeechTranscriber 做字幕的啟發，我也想讓「字幕準確」跟「細粒度時間軸」兼得。**分工跟影像那邊一樣：時間要量，文字要懂。**

SpeechTranscriber（macOS 26 內建）每個字都有起訖時間碼跟信心值，但中文會掉字或同音錯字 —— 實測街訪把「已經濕漉漉了」聽成「已經入入了」。所以讓 Gemini 獨立看一次影片給一份逐字稿，再把正確的字回填到辨識器的時間上。

**模型自己報的秒數一律不採用。** 一個錯的時間戳跟一個對的長得一模一樣，沒辦法用看的檢查。校正過的稿子整段對齊回每字時鐘，每句的頭尾是它自己的字所在的位置，漂移 0.000 秒。人工改字幕走同一條路：沒動到的字保留實測時間，切開一句話時斷點會落在辨識器量到的字界上。

Gemini 回覆時會標出**每句是誰講的**，而且用看得出來的描述 ——「戴黑色漁夫帽的主持人」，不是「說話者一」。剪訪談的時候這比正確的字還有用。

**字幕擺哪裡是交付比例決定的，不是一個常數。** 9:16 底部被帳號、說明文字跟一排按鈕佔走，照傳統貼底就沒人看得到。一行放得下幾個字也不是數字，是拿真正的字型量出來的。**預設一行** —— 逐字稿眼中的「一句」中位數 13 個字，尾巴卻長到 56 個，折成兩行會變成一張臉上壓著五十個中文字。長句是拆成好幾張字幕卡，不是拆成更多行。

字用 Pillow 畫成透明圖再疊上去，不交給 ffmpeg —— 它的文字濾鏡要編進 libass 或 libfreetype，這台機器上兩個都沒有。只用 `overlay` 的話每種 build 都能跑。

## 【決定跟執行要分開】

踩過的坑幾乎都是問錯邊：

- 用程式算邊緣銳利度判斷「這顆好不好看」→ 最好的一顆分數最低
- 讓模型直接給時間戳 → 它會編一個看起來合理的數字
- 用九宮格位置猜主體在哪 → 手機實際在 0.475–0.825，裁切框跑到 0.615

**執行層遇到做不到的事要降級並記錄，不能放棄素材、也不能改掉模型的決定。** 有一次它自作主張把靜止鏡頭換成橫向掃描，下一輪審查回報「掃過去了，字還是被切」—— 整個迴圈在跟自己打架，而做決定的那一層看不到對手是誰。

**做得到什麼跟做不到什麼都要說出口。** 審查層如果不知道這工具沒有文字圖層，就會把「缺字卡」當缺點寫進待修清單 —— 那是一次沒有任何重新規劃能修好的付費呼叫。

**報表跟影片一樣是交付物。** 片子不好看的時候，才知道是哪一層判斷錯了。

## 流程

十二個階段，其中八個要付錢給 Gemini。行首的 `$` 是付費呼叫、`-` 是本機執行，`◈` 是內容定址快取，`〔〕` 是跑這一階的條件。

```
-   毛片 → proxy
    640px；已經剪過的長片先照場景切點拆回鏡頭  ◈
    |
$   Clip Card
    每支素材一次，跨專案共用  ◈
    |
-   Apple ASR  〔有人講話才跑〕
    每字的起訖時間，整條線唯一的時鐘  ◈
    |
$   逐字修正  〔同上〕
    看影片改同音字；它自己報的秒數不採用
    |
$   定調
    片長、比例、哪些素材直接排除
    |
$   選片
    用哪幾顆、進出點、每顆什麼運鏡
    |
$   節奏  〔有配樂才跑〕
    聽音樂重寫長度，並記下哪些本來就不打算對拍
    |
$   主體定位  〔有運鏡才跑〕
    抽靜態格問框，回傳 0..1000 座標
    |
-   SAM 逐幀追蹤  〔同上〕
    本機 propagation，算出每一格的裁切路徑
    |
-   渲染
    ffmpeg 分段 → 串接 → 混音
    |
$   審查  〔--review〕
    看單顆 + 看整片；沒交付的那幾顆送回「主體定位」重跑
    |
-   交付
    mp4、字幕、report.json、FCPXML
```

審查只把「沒做到自己計畫」的那幾顆送回去重新規劃，其他不動。每一輪都是先渲染才審查，所以任何時候停下來都留著一支完整的片。

規劃階段不是只讀卡片文字 —— **定調跟選片都會把所有 proxy 一起附上去重看**。卡片是索引，影片才是判斷依據。選片原本只讀文字摘要，改成附上影片之後它從十一顆變成挑十七顆，並且講出了摘要裡沒有的東西：預覽畫面上的半顆愛心手勢、0.3 公尺的景深讀數、被折起來拿著的手機。**摘要是在還沒人知道這支片要講什麼的時候寫的，所以它省略掉的正好就是選片需要的。**

外部服務只有 Gemini（3.6 Flash，`responseSchema` 綁結構化輸出、`thinking_level: high`）。SAM、語音辨識、節拍分析、ffmpeg 全部在本機跑。

### 兩種素材走不同的路

**畫面配音樂**：切點對上實際量到的重音，運鏡在裁切框裡完成。

**講話為主的片**：一顆鏡頭就是一句話 —— 講完就切，畫面框住正在講話的人，長度由內容決定。原音保留，音樂壓在人聲底下。

不用先說是哪一種，卡片會判斷。

## 怎麼用

```bash
# 需要 Python 3.12 跟 ffmpeg
uv sync                                    # 或 pip install -e .
echo 'GEMINI_API_KEY=...' > .env && set -a && . ./.env && set +a

# 選配：逐幀跟拍要一份 SAM checkpoint（不放也能跑，只是不逐幀追）
#   https://github.com/facebookresearch/sam2 → sam2.1_hiera_tiny.pt

# 選配：逐字稿需要 macOS 26，編一次 Swift 工具
swiftc -parse-as-library -O -o tools/transcribe/transcribe \
  tools/transcribe/Transcribe.swift
```

最短的一次 —— 素材夾進去、9:16 出來，沒給音樂就不配樂：

```bash
montagewright render ~/rushes --aspect 9:16 --output ~/cut
```

**`--brief` 是意圖，不是分鏡表。** 寫「開頭三秒決定一切，每一顆都要有笑點或共鳴點」比寫「第一顆用 A、第二顆用 B」有用得多 —— 前者它會拿去當判斷依據，後者只是把你的工作抄一遍。裡面不要要求字卡、轉場、調色、變速或畫面合成，那些都不在能力範圍內（字幕除外）。

| 選項 | |
|---|---|
| `--review` | 逐顆對照它自己的計畫，沒做到的重新規劃再跑一次。最值得開，也最貴，大概多三到四成 |
| `--budget` | 總上限，包含重跑。碰到就停並交出當下最好的版本，不會為了省錢改用比較差的做法 |
| `--timeline` | `premiere` / `finalcut` / `both`，預設不產生。指回**原始素材**，所以每顆前後都還能往外拉 |
| `--subtitles` | 預設 `sidecar` 寫一份 SRT；`burn` 另外輸出燒好字的版本（原本那支留著）；`none` 不做 |
| `--subtitle-look` | `plain` / `speakers`（每人一色，訪談用）/ `spoken`（講到哪亮到哪）/ `plate`（畫面雜時加底色塊） |
| `--speech` | 預設 `auto`，卡片說「聲音是內容」才做逐字稿，b-roll 不會被收費 |

### 花多少錢

實測（Gemini 3.6 Flash）：

| 這一輪 | 顆數 | 片長 | 花費 |
|---|---|---|---|
| 74 支毛片，第一次跑（要寫 74 張卡片） | 10 | 34.9s | **$1.43** |
| 同一批素材再剪一支（卡片快取） | 22 | 71.0s | **$0.55** |
| 同一批，加音樂與 brief、含重新規劃 | 12 | 43.6s | **$0.67** |
| 5 分半街訪，含逐字稿與重新規劃 | 13 | 48.6s | **$0.81** |
| 同一支再剪一次（卡片與逐字稿都快取） | 16 | 46.1s | **$0.46** |

**第一次最貴，之後便宜很多。** 卡片、逐字稿、proxy 都用檔案內容 hash 快取，同一批素材再剪第二支、第三支都不用重付，也不用重新編碼。

## 網頁介面

```bash
montagewright-web        # http://127.0.0.1:8765
```

![網頁介面](docs/images/web.jpg)

不用記參數，而且跑的過程看得到 —— 寫了幾張卡片、選了幾顆、哪幾顆被重新規劃，中途可以停。

跑完是一個時間軸：視訊軌、人聲與音樂波形、可拖的播放頭。點一顆看它的計畫跟驗收結果，拖邊緣改進出點、拖方塊換順序、× 刪掉，然後重新輸出 —— 這一步不用錢，決定都還在，只是重排。

**可以檢查裁切跟追蹤是真的。** 切到「原素材＋裁切框」會用 proxy 播放並把 9:16 的框畫在上面，跟著時間軸走。這個框是渲染當下真的用的那一個；事後重算的會標「推測」並說明原因。

**字幕可以改完再燒。** 字幕軌每句一格：點一下跳到那句、雙擊改字、拖兩邊改進出點，邊改邊存，改過的會標出來。按「燒進畫面」就用當下的版本輸出，不用錢也不用重跑。

先前的剪輯會留著，重開服務也還在。命令列跑的那些也看得到；中途死掉的也在，因為記錄是開跑前就寫的，已經付過錢的東西都還在硬碟上，接著跑就好。

## 會產出什麼

- **`report.json`** —— 調性、每顆為什麼被選、為什麼是這個長度、每一筆降級跟造成它的量測數字、每個階段花多少錢
- **`work/crops.json`** —— 每顆實際用的裁切路徑，逐個 keyframe。這是「它真的有跟拍」跟「報表說它有跟拍」的差別
- **可編輯的時間軸** —— 指回原始素材檔案，每顆掛著 marker 寫明為什麼選它、哪裡降級、驗收看到什麼
- **字幕 SRT** —— 時間已對齊成片，並標出每句是誰講的
- **燒好字幕的成片** —— 依交付比例的安全區排版，跟原本那支並存

## 程式結構

```
src/montagewright/
  clipcard.py     每支素材的卡片
  transcript.py   逐字稿（本機辨識 + Gemini 修正）
  backfill.py     把校正過的字回填到辨識器的時間上
  planner.py      定調、選片、節奏、主體定位、重新規劃
  capabilities.py 執行層做得到跟做不到的事，同時餵給 prompt 跟 dispatcher
  reframe.py      裁切路徑
  executor.py     EDL → 渲染計畫
  renderer.py     ffmpeg
  review.py       逐顆驗收 + 成片審查
  timeline.py     FCPXML / Premiere XML
  subtitles.py    安全區、斷行、把字燒進畫面
  webapp.py       網頁介面
  measure/        量測：SAM 追蹤、音樂分析、場景偵測、幾何
  prompts/        所有 prompt，繁體中文
```

`measure/` 以外的都在做決定，`measure/` 裡的都在算數字。有一個測試守著這條線：任何 `measure/` 裡的程式 import 上層都會失敗。

撞出來的坑寫在 [`docs/lessons.md`](docs/lessons.md) —— 大部分屬於「東西沒壞但答案是錯的」那一類，留著是因為它們會再發生。舊版設計文件在 `docs/history/`。
