# montagewright

丟一個資料夾的毛片進去，出來一支剪好的片，還有一份說明每個決定是怎麼來的報表。

```bash
montagewright render RUSHES/ --brief BRIEF.md --music TRACK.mp3 \
  --aspect 9:16 --review --output CUT/

montagewright transcribe VIDEO.mp4        # 只要字幕，不重剪
montagewright-web                         # 同一件事，網頁上看得到過程
```

## 它怎麼運作

把「決定」跟「執行」分開：**Gemini 決定這支片是什麼，程式決定那要落在哪一格畫面上。**

Gemini 負責看得懂才能答的問題：

- 這顆素材能不能用、裡面有什麼
- 這批東西該剪成什麼調性、多長、什麼比例
- 用哪幾顆、什麼順序、為什麼
- 每顆要多長、要不要切在拍點上
- 用什麼運鏡、主體擺在畫面哪裡
- 講了什麼、誰在講

程式負責要量才知道的事：

- 拍點實際落在哪一毫秒
- 主體實際在哪一幀的哪個位置（SAM 逐幀追蹤，種子由 Gemini 指定）
- 裁切能走多遠、放大多少會糊

這樣分不是因為信任誰，是因為**兩邊各自只答得出一種問題**。實際踩到的錯，幾乎都是問錯邊造成的 —— 例如讓程式用規則判斷「這顆好不好看」，或讓模型猜「這個東西在第幾幀的哪裡」。

## 支援兩種素材

**畫面配音樂。** 一批毛片加一首歌。切點對上實際量到的重音，運鏡在裁切框裡完成。

**講話為主的片。** 訪談、對鏡頭說話、旁白。這種片一顆鏡頭就是一句話：從那句開始，講完就切，畫面框住正在講話的人。原音保留，音樂壓在人聲底下。

不用先告訴它是哪一種。每支素材的卡片會判斷聲音是不是內容本身，只有是的才會去做逐字稿。

## 一次執行做了什麼

```
clip cards   每支素材寫一張卡片，用內容 hash 快取
transcripts  只有「聲音是內容」的素材才做
direction    看完全部素材 + 音樂 + brief，決定調性、長度、比例
selection    決定用哪幾顆、每顆多長、什麼運鏡、為什麼
rhythm       配合音樂調整每顆的長度與切點
subject      從卡片拿主體位置，拿不到就即時定位一次
reframe      算出裁切路徑
render       分段渲染、串接、混音、產生預覽
review       先逐顆對照它自己的計畫，再看整支
replan       沒做到的那幾顆重新規劃，其他不動
```

卡片刻意不看 brief。因為看著 brief 寫的卡片，換一個 brief 就得重寫；看著素材寫的卡片，素材沒變就一直有效。這樣才值得快取，而快取讓主體位置在重跑時不用再花錢。

丟一支已經剪過的長片進來，它會先照原本的場景切點拆開；如果是一鏡到底的長鏡頭，就保持原樣。

## 會產出什麼

**`report.json`** 記錄全部：調性、每顆為什麼被選、為什麼是這個長度、每一筆降級跟造成它的量測數字、每顆放大了幾倍、以及每個階段花了多少錢。

**可編輯的時間軸**（要加 `--timeline premiere|finalcut|both`，預設不產生）。它指回**原始素材檔案**，所以每顆前後都還能往外拉。每顆上面掛著 marker 寫明為什麼選它、為什麼這個長度、哪裡降級了、驗收時看到什麼。

**字幕 SRT**（有做逐字稿的話），時間已經對齊成片。

## 開發過程學到的事

**用文字要求沒有用，要用結構綁住。** 模型回傳主體位置時會用它自己的 0..1000 座標，不管欄位說明寫得多明確 —— 所以改成收到之後才轉換。同樣地，「某些情況才必填」的欄位標不了 required，只能用必填字串加一個特殊值代表「不適用」。

**只寫在驗證程式裡的規則，之後會用更貴的方式討回來。** 舊版有五條這種規則，每一條都花掉一次完整的付費規劃才被發現，因為模型根本不知道有這些限制。現在所有欄位之間的關聯都寫在模型讀得到的地方。

**欄位常常加在「用到的地方」，卻沒加在「決定的地方」。** 這個錯誤犯了六次。每次都是：欄位定義好了、下游也讀了，但上游根本填不進來。而且不會有任何東西壞掉 —— 預設值看起來合理、影片正常產出，只是那個決定悄悄從企劃層搬到了一個寫死的常數上。

**執行層裡的數字，常常是偽裝成量測的主觀判斷。** 例如 `MAX_UPSCALE` 表面上是技術上限，實際上是在替剪接師回答「這顆值不值得放糊」。又例如音樂音量原本寫成「從音樂本身減 12 dB」，跟人聲一點關係都沒有，結果音樂比人聲還大聲。正確的做法是：程式提供選項跟各自的代價，讓企劃層挑，任何替換都要連同造成它的數字一起記錄。

**執行層不能擅自改掉企劃層選的運鏡。** 有一輪重新規劃時，為了避免文字被裁掉而特地改用靜止鏡頭，結果執行層自作主張換成橫向掃描 —— 下一輪審查回報「掃過去了，字還是被切」。整個迴圈在跟自己打架，而企劃層看不到對手是誰。

**規則要把成立條件講出來。** 「觀眾聽答案就知道問題是什麼」這句只有在畫面上有字卡的時候才成立。寫成通則之後，街訪裡主持人的問句被全部刪光，開場變成一句沒有前提的答案。

**「不會太快」跟「看得懂」是兩回事。** 三台手機用 1.5 秒掃過去，符合每一條速度限制，但觀眾還沒看到第二台就切走了。

**一定要看畫面。** 這個專案每一個構圖問題都是抽出畫格看出來的：掃過頭跑到白色背景牆的鏡頭、推近時瞄準畫面中央而不是主體、字被裁成「y Unpacked」、訪談框到主持人的背影。而這些鏡頭在報表上的移動距離、對點數字全部都是正確的。

**看整支片，看不出單顆的問題。** 有六個構圖錯誤連續通過了整支片的審查，每一個都是單獨打開那一顆才發現的 —— 在三十秒的片子裡，下一顆很快就把上一顆的錯蓋過去了。

## 需要什麼環境

Python 3.12、ffmpeg、`GEMINI_API_KEY`。

用 SAM 追蹤要準備 checkpoint（`--sam-checkpoint`）。要做逐字稿需要 macOS 26，並先編譯一次 Swift 工具：

```bash
swiftc -parse-as-library -O -o tools/transcribe/transcribe \
  tools/transcribe/Transcribe.swift
```

## 關於 `src/jascue_video_lab/`

那裡剩下八個模組，全部都是量測用的：SAM 追蹤、音樂分析，以及它們用到的 geometry、media、models、shots、storage。

上面那層負責決策的程式已經移除了。它把決定寫死在程式碼裡，久了就累積成一堆特例，那正是重寫而不是繼續加東西的理由。量測不用重寫，因為量 4.1 公釐或 117 BPM 這件事，不會因為上面的編輯邏輯換了就變。

舊的設計文件放在 `docs/history/`。
