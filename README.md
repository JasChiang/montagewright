# montagewright

丟一個資料夾的毛片進去，出來一支剪好的片，還有一份說明每個決定是怎麼來的報表。

```bash
montagewright render RUSHES/ --brief BRIEF.md --music TRACK.mp3 \
  --aspect 9:16 --review --output CUT/

montagewright transcribe VIDEO.mp4        # 只要字幕，不重剪
montagewright-web                         # 同一件事，網頁上看得到過程
```

---

如果有人想研究 AI 剪輯但沒什麼頭緒，這裡是我把雲端跟地端接起來的做法。

整套的判斷只有一句：**看得懂才答得出來的問題交給模型，要量才知道的問題交給程式。** 下面兩段其實是同一個問題解兩次 —— Gemini 負責找出那是什麼，本機負責算出它在哪、在第幾秒。

## 【影像】

Gemini 現在可能不是部分使用者的首選模型，不過我一直很喜歡它的「影片理解」跟「圖片理解」。最近有時間就在研究怎麼讓 AI 輔助剪片，這兩項能力確實幫了很多。

手上有一整批毛片的時候，先用 ffmpeg 壓成比較輕量的 proxy（640px / 15fps），再讓 Gemini 整支連聲音看完，整理成一張 Clip Card：這顆拍到什麼、畫面裡可以框住的東西各自在哪個位置、什麼動作發生在第幾秒到第幾秒、攝影機自己有沒有在動、這支的聲音算不算內容。卡片做好就存在本機，用檔案內容的 hash 命名。

**卡片刻意不看 brief。** 看著 brief 寫的卡片，換一個 brief 就得重寫；看著素材寫的卡片，素材沒變就一直有效。所以之後想把同一批素材剪成不同主題或長度，不需要再讓 Gemini 重看全部毛片 —— 先從卡片挑出可能適合的片段，再回到原始影片確認就好。實測第一次跑 74 支要 $1.43，第二支片只要 $0.55。

如果只是一般接片，找到素材其實就可以開始剪了。但如果想把橫式毛片重新構圖成 9:16，或是讓畫面持續跟著人物、手機、產品移動，就還需要知道物件在**每個影格**的位置。

這時候用 [Gemini 的物件偵測](https://ai.google.dev/gemini-api/docs/image-understanding)找出指定物件的定界框 —— 從那顆鏡頭抽五張靜幀送過去，問「左邊那台深色手機」在哪。這件事它做得很好，因為「哪一台是深色的」本來就是語意問題，不是幾何問題。

（一個實際的陷阱：它回傳的是自己的 0..1000 座標系，不管欄位說明寫得多明確，所以換算要在收到的時候做，不能靠 prompt 拜託它。）

不過靜幀只能代表單一時點。一顆 4 秒的鏡頭有 120 幀，主體在中間會移動，抽樣點之間發生什麼事沒人知道；每一幀都問一次是 120 次呼叫，而且時間上還不會連續。所以接著用 **SAM 2.1** 來追蹤 —— 把 Gemini 給的框當種子，往前往後傳播出每一幀的遮罩。追丟的幀會被丟掉並回報比例：曾經發生過九幀只追到兩幀，剩下那一幀變成整段的軌跡，裁切框最後停在一隻手上。

**會動的主體才追**，靜止的直接用卡片裡記的框，一次呼叫都不用。

裁切路徑最後寫成 ffmpeg 的逐幀運算式（緩入緩出的 smoothstep），所以運鏡是連續的，不是幾段跳接。用過的路徑會跟成片一起存下來，所以事後可以把框畫回原素材上，確認它真的有瞄在該瞄的地方。

## 【音訊】

受 Palmier Pro 用 Apple SpeechTranscriber 做字幕的啟發，我也實驗了一套讓「字幕準確度」跟「細粒度時間軸」盡量兼得的轉錄方式。

**Apple SpeechTranscriber**（macOS 26 內建）的強項是時間：每個字都有自己的起訖時間碼，還附信心值。但中文辨識不夠準確，會掉字或同音錯字 —— 實測一段街訪，「已經濕漉漉了」聽成「已經入入了」、「弄乾了」變成「弄幹了」、「回到家」變成「迴到家」。

所以我的做法是讓 **Gemini 獨立看一次影片**，不參考辨識結果先給一份逐字稿，接著把正確的字回填到 SpeechTranscriber 的時間上去。分工的道理跟影像那邊一樣：**時間要量，文字要懂。**

Gemini 回覆時會一併標出**每一句是誰講的**，而且用看得出來的描述 ——「戴黑色漁夫帽的主持人」「穿灰藍色 T 恤的受訪男子」，不是「說話者一」。剪訪談的時候這比正確的字還有用。

斷句用的是標點符號帶的停頓長度。辨識器是連續切的，字跟字之間的間隔全都是 0.000 秒，真正的停頓資訊藏在標點 token 的時間跨度裡。

**字幕擺哪裡是交付比例決定的，不是一個常數。** 9:16 是在 app 裡看的，底部那一塊被帳號、說明文字跟一排按鈕佔走，字幕照傳統位置貼底就是沒人看得到；16:9 沒有這個問題，只要老規矩的 title-safe 邊界就好。而且畫面越窄，一行放得下的字越少 —— 中文又不靠空格斷行，所以「一行幾個字」也不是一個數字，是拿真正的字型量出來的。

**預設一行。** 逐字稿眼中的「一行」是一個句子 —— 中位數 13 個字，但尾巴長到 56 個字。把長句折成兩行的結果是一張臉上壓著五十個中文字，那不是字幕，是一段文章；而縮小字級只會變成小一號的文章。所以長句是**拆成好幾張字幕卡**，不是拆成更多行：在它本來就會停頓的地方切，再按字數分配時間（沒有留逐字時間碼，這個近似在這個長度看不出來）。兩行只留給拆不動的句子，字級也縮不進去的時候 —— 而且是多長一行，不是少講一個字。

其他規則：下一行不能用「，。、！？）」」這類收尾符號開頭（那是中文排版裡最多人一眼看出來的錯，第一次燒出來的畫面就犯了），行尾的標點可以懸出邊界，真的要折兩行的時候平均分。

**一顆鏡頭只抓到半句話，就只顯示那半句。** 本來是時間有裁、字沒裁，所以一顆只留 1 秒的鏡頭會把整句 10 秒的話閃過去。

字是用 Pillow 畫成透明圖再疊上去的，不是交給 ffmpeg —— 它的文字濾鏡要編進 libass 或 libfreetype，而這台機器上的 build 兩個都沒有。只用 `overlay` 的話，每一種 build 都能跑。

這一套也可以單獨用 —— 只想上字幕、不重剪的話：`montagewright transcribe VIDEO.mp4`。

## 【決定跟執行要分開】

踩過的坑幾乎都是問錯邊：

- 用程式算邊緣銳利度判斷「這顆好不好看」→ 最好的一顆分數最低
- 讓模型直接給時間戳 → 它會編一個看起來合理的數字
- 用九宮格位置猜主體在哪 → 手機實際在 0.475–0.825，裁切框跑到 0.615

所以還有三條規則：

**程式遇到做不到的事，要降級並記錄，不能放棄素材、也不能改掉模型的決定。** 推近推不到就推到極限，然後把「想要 0.43、只准 0.66」寫進報表。有一次執行層自作主張把靜止鏡頭換成橫向掃描，下一輪審查回報「掃過去了，字還是被切」—— 整個迴圈在跟自己打架，而做決定的那一層看不到對手是誰。

**做得到什麼跟做不到什麼，都要說出口。** 規劃層不會要求它沒被告知存在的運鏡；同樣地，審查層如果不知道這個工具沒有文字圖層，就會把「缺字卡」當成缺點寫進待修清單 —— 那是一次沒有任何重新規劃能修好的付費呼叫。兩份清單放在同一個檔案裡，一起餵給 prompt。

**報表跟影片一樣是交付物。** 每個決定都說得出是誰做的、為什麼。這樣片子不好看的時候，才知道是哪一層判斷錯了。

## 流程

```
 1. proxy          每支素材壓一份小檔（640px / 15fps）給模型看
 2. clip cards     每支寫一張卡片：內容、主體位置、動作起訖、需要什麼處理
 3. transcripts    只有卡片說「聲音是內容」的素材才做逐字稿
 4. direction      看完全部 + 音樂 + brief → 調性、長度、比例、音樂怎麼鋪
 5. selection      → 用哪幾顆、從第幾秒進、多長、什麼運鏡、為什麼
 6. rhythm         → 配合音樂微調長度與切點
 7. subject        主體在哪：卡片有就用，沒有就即時定位一次
 8. track          SAM 逐幀追蹤（會動的主體才做）
 9. reframe        算出裁切路徑
10. render         分段渲染 → 串接 → 混音 → 預覽
11. review         先逐顆對照它自己的計畫，再看整支
12. replan         沒做到的那幾顆重新規劃，其他不動，然後重跑 7–11
```

**丟一支已經剪過的長片進來**，第 1 步之前會先照原本的場景切點拆開；如果是一鏡到底，就保持原樣。

外部服務只有 Gemini（3.6 Flash，用 `responseSchema` 綁結構化輸出、`thinking_level: high`）。SAM、語音辨識、節拍分析、ffmpeg 全部在本機跑。上傳過的 proxy 用內容 hash 快取 48 小時，重跑不用重傳；proxy 本身也是內容定址的，同一批素材剪第二次不用重新編碼。

### 兩種素材走不同的路

**畫面配音樂**：切點對上實際量到的重音，運鏡在裁切框裡完成。

**講話為主的片**：一顆鏡頭就是一句話 —— 從那句開始，講完就切，畫面框住正在講話的人，長度由內容決定（不對拍點）。原音保留，音樂壓在人聲底下。

不用先說是哪一種，卡片會判斷。

## 怎麼用

### 裝起來

```bash
# 需要 Python 3.12 跟 ffmpeg
uv sync                      # 或 pip install -e .

# API key
echo 'GEMINI_API_KEY=...' > .env
set -a && . ./.env && set +a

# 想要逐幀跟拍的話，放一份 SAM checkpoint（不放也能跑，只是不會逐幀追）
#   https://github.com/facebookresearch/sam2 → sam2.1_hiera_tiny.pt

# 想做逐字稿的話（需要 macOS 26），編一次 Swift 工具
swiftc -parse-as-library -O -o tools/transcribe/transcribe \
  tools/transcribe/Transcribe.swift
```

### 最短的一次

```bash
montagewright render ~/rushes --aspect 9:16 --output ~/cut
```

素材夾進去、9:16 出來。沒給音樂就不配樂，長度全部由內容決定。

### 實際會用的那一行

```bash
montagewright render ~/rushes \
  --brief BRIEF.md \
  --music track.mp3 \
  --aspect 9:16 \
  --sam-checkpoint artifacts/models/sam2.1_hiera_tiny.pt \
  --review \
  --timeline both \
  --budget 6 \
  --output ~/cut
```

### 選項裡值得說的

**`--brief` 是意圖，不是分鏡表。** 寫「這支要讓人想點進去看完整版，開頭三秒決定一切，每一顆都要有笑點或共鳴點」比寫「第一顆用 A、第二顆用 B」有用得多 —— 前者它會拿去當判斷依據，後者只是把你的工作抄一遍。實測同一批素材，加了這種 brief 之後開場整個換掉了。

（brief 裡不要要求字卡、轉場、調色、變速或畫面合成，這些都不在能力範圍內 —— 字幕除外，那個做得到。審查層知道這些界線，不會把它們寫成待修項目，但規劃層也生不出來。）

**`--review`** 打開之後會多做兩件事：**逐顆對照它自己的計畫**（這顆說要推近到鏡頭模組，推到了嗎？說 3.5 秒是為了讓動作做完，做完了嗎？），還有**沒做到的那幾顆重新規劃再跑一次**。這是最值得開的選項，也是最花錢的 —— 大概多三到四成。

**`--timeline`** 預設不產生。要在 Premiere／Final Cut 裡改的時候才加。它指回**原始素材**，所以每顆前後都還能往外拉。

**`--subtitles`** 預設 `sidecar`，會在成片旁邊寫一份 SRT。`burn` 會多輸出一支把字燒進畫面的版本（原本那支留著，燒進去的字拿不掉，要發哪一支不該由這個工具決定）。`none` 是完全不做。

**`--speech`** 預設 `auto` —— 卡片說「這支的聲音是內容」才做逐字稿，b-roll 不會被收費。`never` 是強制關掉。

**`--budget`** 是總上限，包含重新規劃跟重跑。碰到就停，然後交出當下最好的版本 —— 不會為了省錢改用比較差的做法。

**`--music-map`** 幾乎用不到。給 `--music` 就會自己量節拍；這個是給已經人工審過的節拍表用的。

### 花多少錢

實測（Gemini 3.6 Flash）：

| 這一輪 | 顆數 | 片長 | 花費 |
|---|---|---|---|
| 74 支毛片，第一次跑（要寫 74 張卡片） | 10 | 34.9s | **$1.43** |
| 同一批素材再剪一支（卡片快取） | 22 | 71.0s | **$0.55** |
| 同一批，加音樂與 brief、含重新規劃 | 12 | 43.6s | **$0.67** |
| 5 分半街訪，含逐字稿與重新規劃 | 13 | 48.6s | **$0.81** |
| 同一支再剪一次（卡片與逐字稿都快取） | 16 | 46.1s | **$0.46** |

**第一次最貴，之後便宜很多。** 卡片跟逐字稿用檔案內容 hash 快取，同一批素材再剪第二支、第三支都不用重付。

## 網頁介面

```bash
montagewright-web        # http://127.0.0.1:8765
```

不用記參數，而且跑的過程看得到。

![網頁介面](docs/images/web.jpg)

**選素材不用打路徑。** 點「瀏覽…」直接挑資料夾，每一層會標有幾支影片，所以一眼看得出哪個是毛片。（本機素材建議用路徑 —— 上傳等於把硬碟上的檔案搬進瀏覽器再寫回去，一支 5 分鐘的 4K 是 800 MB。）

**跑的時候**即時串出每一行進度：寫了幾張卡片、幾支有語音、選了幾顆、逐顆驗收過了幾顆、哪幾顆被重新規劃。中途可以停。

**跑完是一個時間軸**：視訊軌、人聲與音樂的波形、可以拖的播放頭。點一顆就在右邊看到它的計畫跟驗收結果，拖邊緣改進出點、拖方塊換順序、× 刪掉，然後重新輸出 —— 這一步不用錢，因為決定都還在，只是重排。

**可以檢查裁切跟追蹤是真的。** 切到「原素材＋裁切框」，就會用原素材的 proxy 播放，把 9:16 的裁切框畫在上面，跟著時間軸一起走。橫搖看得到框在移動，推近看得到框在收緊，標籤會說「橫搖　偏左 → 偏右　現在 置中」。這個框是渲染當下真的用的那一個 —— 舊版的執行沒有留下記錄，事後重算的框會標「推測」並說明原因。

**字幕可以改完再燒。** 字幕軌在視訊軌下面，每句一格：點一下跳到那句、雙擊改字、拖兩邊改進出點，邊改邊存。改過的那幾句會標出來。按「燒進畫面」就用當下的版本輸出一支燒好字的片，不用錢也不用重跑。

**跑完還會看到：** 分階段花費、每一顆用了什麼怎麼處理、逐字稿（含誰講的、Gemini 改了哪些字）、沒有用的素材跟卡片給的理由、完整畫質與字幕 SRT 與兩種 timeline 的下載。

**先前的剪輯會留著。** 重開服務也還在，可以直接點開比較 —— 片長、顆數、逐顆通過幾顆、花了多少。命令列跑的那些也看得到，`--output` 指到哪裡都一樣；中途死掉的那些也在，因為記錄是開跑前就寫的，而已經付過錢的東西都還在硬碟上，接著跑就好。

## 會產出什麼

**`report.json`** —— 調性、每顆為什麼被選、為什麼是這個長度、每一筆降級跟造成它的量測數字、每顆放大幾倍、每個階段花多少錢。

**`work/crops.json`** —— 每一顆實際用的裁切路徑，逐個 keyframe。這是「它真的有跟拍」跟「報表說它有跟拍」的差別。

**可編輯的時間軸**（`--timeline premiere|finalcut|both`）—— 指回**原始素材檔案**，所以每顆前後都還能往外拉。每顆掛著 marker 寫明為什麼選它、為什麼這個長度、哪裡降級、驗收看到什麼。

**字幕 SRT**（有做逐字稿的話），時間已經對齊成片，並標出每句是誰講的。

**燒好字幕的成片**（`--subtitles burn`，或事後在網頁上按「燒進畫面」）—— 依交付比例的安全區排版，跟原本那支並存。

## 程式結構

```
src/montagewright/
  clipcard.py    每支素材的卡片
  transcript.py  逐字稿（本機辨識 + Gemini 修正）
  planner.py     定調、選片、節奏、主體定位、重新規劃
  capabilities.py 執行層做得到跟做不到的事，同時餵給 prompt 跟 dispatcher
  reframe.py     裁切路徑
  executor.py    EDL → 渲染計畫
  renderer.py    ffmpeg
  review.py      逐顆驗收 + 成片審查
  timeline.py    FCPXML / Premiere XML
  subtitles.py   安全區、斷行、把字燒進畫面
  webapp.py      網頁介面
  measure/       量測：SAM 追蹤、音樂分析、場景偵測、幾何
  prompts/       所有 prompt，繁體中文
```

`measure/` 以外的都在做決定，`measure/` 裡的都在算數字。有一個測試在守這條線：任何 `measure/` 裡的程式 import 上層都會失敗。

做這個工具的時候撞出來的坑寫在 [`docs/lessons.md`](docs/lessons.md) —— 大部分屬於「東西沒壞但答案是錯的」那一類，留著是因為它們會再發生。舊版的設計文件放在 `docs/history/`。
