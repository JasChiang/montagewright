# montagewright

丟一個資料夾的毛片進去，出來一支剪好的片，還有一份說明每個決定是怎麼來的報表。

```bash
montagewright render RUSHES/ --brief BRIEF.md --music TRACK.mp3 \
  --aspect 9:16 --review --output CUT/

montagewright transcribe VIDEO.mp4        # 只要字幕，不重剪
montagewright-web                         # 同一件事，網頁上看得到過程
```

---

## 它怎麼把一堆毛片變成一支片

### 第一步：讓 Gemini 真的看過每一支素材

不是讀檔名、不是抽幾張圖 —— **整支影片連聲音送給 Gemini**，它看得懂畫面也聽得到人在講什麼。

每支素材看完寫一張卡片，記下：這顆在拍什麼、可以框住的東西各自在畫面哪個位置、有什麼動作發生在第幾秒到第幾秒、攝影機自己有沒有在動、這支的聲音是不是內容本身。

卡片用檔案內容的 hash 快取。同一批素材再剪第二支片，這一步是免費的。

### 第二步：如果有人在講話，先聽懂他在說什麼

卡片說「聲音是內容」的素材（訪談、對鏡頭講話、旁白），會多跑一步。

**Apple 的 SpeechTranscriber**（macOS 26 內建的語音辨識）把整段轉成逐字稿。它厲害的地方是**逐字時間戳** —— 每一個字從第幾秒到第幾秒，還附上信心值。

但它常常聽錯字。實測一段街訪：「已經濕漉漉了」聽成「已經入入了」、「弄乾了」變成「弄幹了」、「回到家」變成「迴到家」。

所以**文字交給 Gemini 改**。Gemini 拿到影片、聲音、跟辨識器的原始結果，一起看完之後把字改對。它還會標出**每一句是誰講的** —— 用「戴黑色漁夫帽的主持人」「穿灰藍色T恤的受訪男子」這種看得出來的描述，不是「說話者一」。

分工的道理很簡單：**時間要量，文字要懂**。辨識器量時間很準，理解上下文不是它的強項；Gemini 反過來。

### 第三步：Gemini 決定這支片怎麼剪

看完全部素材（加上音樂、加上你寫的 brief），它決定：

- 這批東西適合剪成什麼調性、多長、什麼比例
- 用哪幾顆、什麼順序
- 每顆從第幾秒進、放多久
- 每顆用什麼運鏡、畫面要框住誰
- 音樂該壓在人聲底下當底襯，還是跟著人聲起伏，還是不要音樂

每一個決定都要寫理由，而且理由要用畫面上實際看得到的東西講。

### 第四步：找出主體在畫面的哪裡

Gemini 說「框住左邊那台深色手機」—— 但畫面上有三台手機，程式怎麼知道是哪一台？

**先問 Gemini。** 從那顆鏡頭抽五張靜幀送過去，用 [Gemini 的物件偵測](https://ai.google.dev/gemini-api/docs/image-understanding)拿到框：那台手機在每一張的中心點跟寬高各是多少。這件事它做得很好，因為「哪一台是深色的」本來就是語意問題。

（一個實際的陷阱：它回傳的是自己的 0..1000 座標系，不管欄位說明寫得多明確。所以轉換在收到的時候做，不是靠 prompt 拜託它。）

**但五張靜幀不是一段軌跡。** 一顆 4 秒的鏡頭有 120 幀，主體在中間會移動；抽樣點之間發生什麼事沒人知道，而每一幀都問一次是 120 次呼叫，而且時間上不會連續。

**所以逐幀交給 SAM 2.1。** 把 Gemini 給的框當種子丟進去，SAM 往前往後傳播出每一幀的遮罩。追丟的幀會被丟掉並回報比例 —— 曾經發生過九幀只追到兩幀，剩下那一幀變成整段的軌跡，裁切框最後停在一隻手上。

**會動的主體才追。** 靜止的直接用卡片裡記的框，一次呼叫都不用。

### 第五步：ffmpeg 把決定變成畫面

裁切路徑寫成逐幀運算式（所以運鏡是連續的，不是幾段跳接）、分段渲染、串接、混音。

有人聲的片子會先把人聲拉平（不同受訪者音量差很多），再把音樂壓到人聲底下 14 dB。沒人聲的片子就對響度標準化到 -14 LUFS。

### 為什麼要這樣分工

一句話：**看得懂才答得出來的問題給 Gemini，要量才知道的問題給程式。**

實際踩過的坑都是問錯邊：

- 用程式算邊緣銳利度來判斷「這顆好不好看」→ 結果最好的一顆分數最低
- 讓模型直接給時間戳 → 它會編一個看起來合理的數字
- 用九宮格位置猜主體在哪 → 手機實際在 0.475–0.825，裁切框跑到 0.615

還有兩條規則：

**程式遇到做不到的事，要降級並記錄，不能放棄素材、也不能改掉 Gemini 的決定。** 推近推不到就推到極限，然後把「想要 0.43、只准 0.66」寫進報表。有一次執行層自作主張把靜止鏡頭換成橫向掃描，下一輪審查回報「掃過去了，字還是被切」—— 整個迴圈在跟自己打架，而做決定的那一層看不到對手是誰。

**報表跟影片一樣是交付物。** 每個決定都說得出是誰做的、為什麼。這樣片子不好看的時候，才知道是哪一層判斷錯了。

## 流程

```
 1. proxy          每支素材壓一份小檔（640px / 15fps）給模型看
 2. clip cards     每支寫一張卡片：內容、主體位置、動作起訖、需要什麼處理
 3. transcripts    只有卡片說「聲音是內容」的素材才做逐字稿
 4. direction      看完全部 + 音樂 + brief → 調性、長度、比例、音樂怎麼鋪
 5. selection      → 用哪幾顆、從第幾秒進、多長、什麼運鏡、為什麼
 6. rhythm         → 配合音樂微調長度與切點
 7. subject        主體在哪：卡片有就用，沒有就即時定位一次
 8. track          SAM 逐幀追蹤（會動的主體才做）
 9. reframe        算出裁切路徑
10. render         分段渲染 → 串接 → 混音 → 預覽
11. review         先逐顆對照它自己的計畫，再看整支
12. replan         沒做到的那幾顆重新規劃，其他不動，然後重跑 7–11
```

**卡片刻意不看 brief。** 因為看著 brief 寫的卡片，換一個 brief 就得重寫；看著素材寫的卡片，素材沒變就一直有效。這樣才值得用內容 hash 快取，而快取讓主體位置在重跑時不用再花錢。

**丟一支已經剪過的長片進來**，第 1 步之前會先照原本的場景切點拆開；如果是一鏡到底，就保持原樣。

### 兩種素材走不同的路

**畫面配音樂**：切點對上實際量到的重音，運鏡在裁切框裡完成。

**講話為主的片**：一顆鏡頭就是一句話 —— 從那句開始，講完就切，畫面框住正在講話的人，長度由內容決定（不對拍點）。原音保留，音樂壓在人聲底下。

不用先說是哪一種，卡片會判斷。

外部服務只有 Gemini（3.6 Flash，用 `responseSchema` 綁結構化輸出、`thinking_level: high`）。SAM、語音辨識、節拍分析、ffmpeg 全部在本機跑。上傳過的 proxy 會用內容 hash 快取 48 小時，重跑不用重傳。

## 怎麼用

### 第一次

```bash
# 1. 裝起來（需要 Python 3.12 跟 ffmpeg）
uv sync                      # 或 pip install -e .

# 2. API key
echo 'GEMINI_API_KEY=...' > .env
set -a && . ./.env && set +a

# 3. 要用 SAM 追蹤的話，放一份 checkpoint（不放也能跑，只是不會逐幀跟拍）
#    https://github.com/facebookresearch/sam2 → sam2.1_hiera_tiny.pt

# 4. 要做逐字稿的話（需要 macOS 26），編一次 Swift 工具
swiftc -parse-as-library -O -o tools/transcribe/transcribe \
  tools/transcribe/Transcribe.swift
```

### 最短的一次

```bash
montagewright render ~/rushes --aspect 9:16 --output ~/cut
```

素材夾進去、9:16 出來。沒給音樂就不配樂，長度全部由內容決定。

### 實際會用的那一行

```bash
montagewright render ~/rushes \
  --brief BRIEF.md \
  --music track.mp3 \
  --aspect 9:16 \
  --sam-checkpoint artifacts/models/sam2.1_hiera_tiny.pt \
  --review \
  --timeline both \
  --budget 6 \
  --output ~/cut
```

### 選項裡值得說的

**`--brief`** 是**意圖，不是分鏡表**。寫「這支要讓人想點進去看完整版，開頭三秒決定一切，每一顆都要有笑點或共鳴點」比寫「第一顆用 A、第二顆用 B」有用得多 —— 前者它會拿去當判斷依據，後者只是把你的工作抄一遍。實測同一批素材，加了這種 brief 之後開場整個換掉了。

**`--review`** 打開之後會多做兩件事：**逐顆對照它自己的計畫**（這顆說要推近到鏡頭模組，推到了嗎？說 3.5 秒是為了讓動作做完，做完了嗎？），還有**沒做到的那幾顆重新規劃再跑一次**。這是最值得開的選項，也是最花錢的 —— 大概多三到四成。

**`--timeline`** 預設不產生。要在 Premiere／Final Cut 裡改的時候才加。它指回**原始素材**，所以每顆前後都還能往外拉。

**`--speech`** 預設 `auto` —— 卡片說「這支的聲音是內容」才做逐字稿，b-roll 不會被收費。`never` 是強制關掉。

**`--budget`** 是總上限，包含重新規劃跟重跑。碰到就停，然後交出當下最好的版本 —— 不會為了省錢改用比較差的做法。

**`--music-map`** 幾乎用不到。給 `--music` 就會自己量節拍；這個是給已經人工審過的節拍表用的。

### 花多少錢

實測（Gemini 3.6 Flash）：

| 這一輪 | 顆數 | 片長 | 花費 |
|---|---|---|---|
| 74 支毛片，第一次跑（要寫 74 張卡片） | 10 | 34.9s | **$1.43** |
| 同一批素材再剪一支（卡片快取） | 22 | 71.0s | **$0.55** |
| 5 分半街訪，含逐字稿與重新規劃 | 13 | 48.6s | **$0.81** |
| 同一支再剪一次（卡片與逐字稿都快取） | 16 | 46.1s | **$0.46** |

**第一次最貴，之後便宜很多。** 卡片跟逐字稿用檔案內容 hash 快取，同一批素材再剪第二支、第三支都不用重付。

## 網頁介面

```bash
montagewright-web        # http://127.0.0.1:8765
```

不用記參數，而且跑的過程看得到。

![網頁介面](docs/images/web.jpg)

**選素材不用打路徑。** 點「瀏覽…」直接挑資料夾，每一層會標有幾支影片，所以一眼看得出哪個是毛片。（本機素材建議用路徑 —— 上傳等於把硬碟上的檔案搬進瀏覽器再寫回去，一支 5 分鐘的 4K 是 800 MB。）

**跑的時候**即時串出每一行進度：寫了幾張卡片、幾支有語音、選了幾顆、逐顆驗收過了幾顆、哪幾顆被重新規劃。中途可以停。

**跑完會看到：**

- 影片，加上完整畫質、字幕 SRT、兩種 timeline 的下載
- **分階段花費**（哪一步最貴，一目瞭然）
- **每一顆用了什麼、怎麼處理** —— 素材檔名（點下去單獨看那一顆）、從第幾秒進、多長、什麼運鏡、框住誰、為什麼選它、降級了什麼、逐顆驗收看到什麼
- **聽到了什麼** —— 逐字稿，含時間、誰講的、Gemini 改了什麼字
- **沒有用的素材** 跟卡片給的理由

**先前的剪輯會留著。** 重開服務也還在，可以直接點開跟這一輪比較 —— 片長、顆數、逐顆通過幾顆、花了多少。

## 會產出什麼

**`report.json`** —— 調性、每顆為什麼被選、為什麼是這個長度、每一筆降級跟造成它的量測數字、每顆放大幾倍、每個階段花多少錢。

**可編輯的時間軸**（`--timeline premiere|finalcut|both`，預設不產生）—— 指回**原始素材檔案**，所以每顆前後都還能往外拉。每顆掛著 marker 寫明為什麼選它、為什麼這個長度、哪裡降級、驗收看到什麼。

**字幕 SRT**（有做逐字稿的話），時間已經對齊成片。

## 程式結構

```
src/montagewright/
  clipcard.py    每支素材的卡片
  transcript.py  逐字稿（本機辨識 + Gemini 修正）
  planner.py     定調、選片、節奏、主體定位、重新規劃
  capabilities.py 執行層做得到的運鏡，同時餵給 prompt 跟 dispatcher
  reframe.py     裁切路徑
  executor.py    EDL → 渲染計畫
  renderer.py    ffmpeg
  review.py      逐顆驗收 + 成片審查
  timeline.py    FCPXML / Premiere XML
  measure/       量測：SAM 追蹤、音樂分析、場景偵測、幾何
  prompts/       所有 prompt，繁體中文
```

`measure/` 以外的都在做決定，`measure/` 裡的都在算數字。有一個測試在守這條線：任何 `measure/` 裡的程式 import 上層都會失敗。

舊版的設計文件放在 `docs/history/`。

做這個工具的時候撞出來的坑，寫在 [`docs/lessons.md`](docs/lessons.md) —— 大部分屬於
「東西沒壞但答案是錯的」，留著是因為它們會再發生。
