# montagewright

丟一個資料夾的毛片進去，出來一支剪好的片，還有一份說明每個決定是怎麼來的報表。

```bash
montagewright render RUSHES/ --brief BRIEF.md --music TRACK.mp3 \
  --aspect 9:16 --review --output CUT/

montagewright transcribe VIDEO.mp4        # 只要字幕，不重剪
montagewright-web                         # 同一件事，網頁上看得到過程
```

---

## 原理

### 一句話

**Gemini 決定這支片是什麼，程式決定那要落在哪一格畫面上。**

### 為什麼要這樣分

這兩邊各自只答得出一種問題。

「這顆鏡頭在講什麼」「這句話好不好笑」「這支片該用什麼調性」—— 這些**要看得懂才答得出來**，寫規則永遠會漏。

「重音落在第 12.484 秒」「那台手機在第 37 幀的 x=0.65」「放大 1.8 倍會不會糊」—— 這些**要量才知道**，模型猜出來的數字沒有意義。

實際踩到的錯，幾乎都是問錯邊：

- 讓程式用邊緣銳利度判斷「這顆好不好看」→ 結果最好的一顆分數最低
- 讓模型直接給時間戳 → 它會編一個看起來合理的數字
- 讓程式用九宮格位置猜主體在哪 → 手機在 0.475–0.825，裁切框跑到 0.615

### 第二條原則：執行層沒有否決權

程式遇到做不到的事情時，**降級並記錄**，不能放棄素材、也不能改掉企劃層的決定。

推近推不到想要的倍數，就推到能推的極限，然後把「想要 0.43、只准 0.66」寫進報表。追蹤掉了一半的幀，就用剩下的，然後記下掉了多少。

這條規則是踩出來的：有一輪重新規劃為了避免文字被裁掉而特地改用靜止鏡頭，執行層自作主張換成橫向掃描，下一輪審查回報「掃過去了，字還是被切」。整個迴圈在跟自己打架，而企劃層看不到對手是誰。

### 第三條：報表跟影片一樣是交付物

每一個決定都要說得出是誰做的、為什麼。降級要附上造成它的數字。這樣才有辦法在片子不好看的時候，知道是哪一層判斷錯了。

## 流程

```
 1. proxy          每支素材壓一份小檔（640px / 15fps）給模型看
 2. clip cards     每支寫一張卡片：內容、主體位置、動作起訖、需要什麼處理
 3. transcripts    只有卡片說「聲音是內容」的素材才做逐字稿
 4. direction      看完全部 + 音樂 + brief → 調性、長度、比例、音樂怎麼鋪
 5. selection      → 用哪幾顆、從第幾秒進、多長、什麼運鏡、為什麼
 6. rhythm         → 配合音樂微調長度與切點
 7. subject        主體在哪：卡片有就用，沒有就即時定位一次
 8. track          SAM 逐幀追蹤（會動的主體才做）
 9. reframe        算出裁切路徑
10. render         分段渲染 → 串接 → 混音 → 預覽
11. review         先逐顆對照它自己的計畫，再看整支
12. replan         沒做到的那幾顆重新規劃，其他不動，然後重跑 7–11
```

**卡片刻意不看 brief。** 因為看著 brief 寫的卡片，換一個 brief 就得重寫；看著素材寫的卡片，素材沒變就一直有效。這樣才值得用內容 hash 快取，而快取讓主體位置在重跑時不用再花錢。

**丟一支已經剪過的長片進來**，第 1 步之前會先照原本的場景切點拆開；如果是一鏡到底，就保持原樣。

### 兩種素材走不同的路

**畫面配音樂**：切點對上實際量到的重音，運鏡在裁切框裡完成。

**講話為主的片**：一顆鏡頭就是一句話 —— 從那句開始，講完就切，畫面框住正在講話的人，長度由內容決定（不對拍點）。原音保留，音樂壓在人聲底下。

不用先說是哪一種，卡片會判斷。

## 用了哪些工具

| 工具 | 做什麼 | 為什麼是它 |
|---|---|---|
| **Gemini 3.6 Flash** | 全部的判斷：卡片、定調、選片、節奏、運鏡、逐顆驗收 | 看得懂影片，也聽得到聲音。用 `responseSchema` 綁結構化輸出，`thinking_level: high` |
| **Gemini File API** | 上傳 proxy 供多次呼叫重用 | 一批 74 支素材要送給定調、選片、多輪審查。48 小時內用內容 hash 快取，重跑不用重傳 |
| **SAM 2.1** | 逐幀追蹤主體 | Gemini 給種子框（哪一個），SAM 給每一幀的位置（在哪裡）。追丟的幀會被丟掉並回報比例 |
| **Apple SpeechTranscriber** | 語音轉逐字稿 | macOS 26 內建，**逐字時間戳加信心值**，離線、免費、zh-TW 內建。它時間很準、文字常錯，所以文字交給 Gemini 改 |
| **ffmpeg** | 全部的影像與聲音處理 | proxy、抽格、逐幀運算式裁切、串接、`loudnorm` + `alimiter` 響度、`sidechaincompress` 閃避、`speechnorm` 人聲拉平 |
| **本機音訊分析** | 節拍與段落邊界 | 產出可切的 cue 清單，讓「第八拍」「副歌開始」這種說法解析成真實毫秒 |

外部服務只有 Gemini。其他全部在本機跑。

## 會產出什麼

**`report.json`** —— 調性、每顆為什麼被選、為什麼是這個長度、每一筆降級跟造成它的量測數字、每顆放大幾倍、每個階段花多少錢。

**可編輯的時間軸**（`--timeline premiere|finalcut|both`，預設不產生）—— 指回**原始素材檔案**，所以每顆前後都還能往外拉。每顆掛著 marker 寫明為什麼選它、為什麼這個長度、哪裡降級、驗收看到什麼。

**字幕 SRT**（有做逐字稿的話），時間已經對齊成片。

## 開發過程學到的事

**用文字要求沒有用，要用結構綁住。** 模型回傳主體位置時會用它自己的 0..1000 座標，不管欄位說明寫得多明確 —— 所以改成收到之後才轉換。同樣地，「某些情況才必填」的欄位標不了 required，只能用必填字串加一個特殊值代表「不適用」。

**只寫在驗證程式裡的規則，之後會用更貴的方式討回來。** 舊版有五條這種規則，每一條都花掉一次完整的付費規劃才被發現，因為模型根本不知道有這些限制。現在所有欄位之間的關聯都寫在模型讀得到的地方。

**欄位常常加在「用到的地方」，卻沒加在「決定的地方」。** 這個錯誤犯了六次。每次都是欄位定義好了、下游也讀了，但上游根本填不進來。而且不會有任何東西壞掉 —— 預設值看起來合理、影片正常產出，只是那個決定悄悄從企劃層搬到了一個寫死的常數上。

**執行層裡的數字，常常是偽裝成量測的主觀判斷。** `MAX_UPSCALE` 表面上是技術上限，實際上是在替剪接師回答「這顆值不值得放糊」。音樂音量原本寫成「從音樂本身減 12 dB」，跟人聲一點關係都沒有，結果音樂比人聲還大聲。正確做法是：程式提供選項跟各自的代價，讓企劃層挑，任何替換都連同造成它的數字一起記錄。

**規則要把成立條件講出來。** 「觀眾聽答案就知道問題是什麼」只有在畫面上有字卡時才成立。寫成通則之後，街訪裡主持人的問句被全部刪光，開場變成一句沒有前提的答案。

**「不會太快」跟「看得懂」是兩回事。** 三台手機用 1.5 秒掃過去符合每一條速度限制，但觀眾還沒看到第二台就切走了。

**一定要看畫面。** 每一個構圖問題都是抽出畫格看出來的：掃過頭跑到白色背景牆、推近時瞄準畫面中央而不是主體、字被裁成「y Unpacked」、訪談框到主持人的背影。而這些鏡頭在報表上的移動距離、對點數字全部都是正確的。

**看整支片，看不出單顆的問題。** 有六個構圖錯誤連續通過了整支片的審查，每一個都是單獨打開那一顆才發現的 —— 三十秒的片子裡，下一顆很快就把上一顆的錯蓋過去。

## 需要什麼環境

Python 3.12、ffmpeg、`GEMINI_API_KEY`。

SAM 追蹤要準備 checkpoint（`--sam-checkpoint`）。逐字稿需要 macOS 26，並先編譯一次 Swift 工具：

```bash
swiftc -parse-as-library -O -o tools/transcribe/transcribe \
  tools/transcribe/Transcribe.swift
```

## 程式結構

```
src/montagewright/
  clipcard.py    每支素材的卡片
  transcript.py  逐字稿（本機辨識 + Gemini 修正）
  planner.py     定調、選片、節奏、主體定位、重新規劃
  capabilities.py 執行層做得到的運鏡，同時餵給 prompt 跟 dispatcher
  reframe.py     裁切路徑
  executor.py    EDL → 渲染計畫
  renderer.py    ffmpeg
  review.py      逐顆驗收 + 成片審查
  timeline.py    FCPXML / Premiere XML
  measure/       量測：SAM 追蹤、音樂分析、場景偵測、幾何
  prompts/       所有 prompt，繁體中文
```

`measure/` 以外的都在做決定，`measure/` 裡的都在算數字。有一個測試在守這條線：任何 `measure/` 裡的程式 import 上層都會失敗。

舊版的設計文件放在 `docs/history/`。
