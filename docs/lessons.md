# 開發過程學到的事

這些是做這個工具的時候撞出來的，大部分是「東西沒壞但答案是錯的」那一類。
留在這裡是因為它們會再發生，不是因為它們已經解決了。

**用文字要求沒有用，要用結構綁住。** 模型回傳主體位置時會用它自己的 0..1000 座標，不管欄位說明寫得多明確 —— 所以改成收到之後才轉換。同樣地，「某些情況才必填」的欄位標不了 required，只能用必填字串加一個特殊值代表「不適用」。

**只寫在驗證程式裡的規則，之後會用更貴的方式討回來。** 舊版有五條這種規則，每一條都花掉一次完整的付費規劃才被發現，因為模型根本不知道有這些限制。現在所有欄位之間的關聯都寫在模型讀得到的地方。

**欄位常常加在「用到的地方」，卻沒加在「決定的地方」。** 這個錯誤犯了六次。每次都是欄位定義好了、下游也讀了，但上游根本填不進來。而且不會有任何東西壞掉 —— 預設值看起來合理、影片正常產出，只是那個決定悄悄從企劃層搬到了一個寫死的常數上。

**執行層裡的數字，常常是偽裝成量測的主觀判斷。** `MAX_UPSCALE` 表面上是技術上限，實際上是在替剪接師回答「這顆值不值得放糊」。音樂音量原本寫成「從音樂本身減 12 dB」，跟人聲一點關係都沒有，結果音樂比人聲還大聲。正確做法是：程式提供選項跟各自的代價，讓企劃層挑，任何替換都連同造成它的數字一起記錄。

**規則要把成立條件講出來。** 「觀眾聽答案就知道問題是什麼」只有在畫面上有字卡時才成立。寫成通則之後，街訪裡主持人的問句被全部刪光，開場變成一句沒有前提的答案。

**「不會太快」跟「看得懂」是兩回事。** 三台手機用 1.5 秒掃過去符合每一條速度限制，但觀眾還沒看到第二台就切走了。

**一定要看畫面。** 每一個構圖問題都是抽出畫格看出來的：掃過頭跑到白色背景牆、推近時瞄準畫面中央而不是主體、字被裁成「y Unpacked」、訪談框到主持人的背影。而這些鏡頭在報表上的移動距離、對點數字全部都是正確的。

**看整支片，看不出單顆的問題。** 有六個構圖錯誤連續通過了整支片的審查，每一個都是單獨打開那一顆才發現的 —— 三十秒的片子裡，下一顆很快就把上一顆的錯蓋過去。

**「事後重算」跟「當時做的事」不是同一件事。** 網頁上畫在原素材上的裁切框，本來是每次打開再從素材卡算一次。素材卡叫不出名字的主體就退回畫面正中央 —— 於是十三顆全部裁在中央、標籤全部一樣，而報表裡寫的是它跟過的主體。畫面看起來像證據，其實是猜的。追蹤是 SAM propagation 加上一次 grounding 的結果，事後沒有 checkpoint 也沒有 client，本來就重算不出來。現在渲染當下就把用過的裁切路徑寫下來，重算的會標「推測」並說明。

**內容定址的東西，不能用檔名當 key。** 素材卡是用 proxy 的 content hash 命名的，兩個地方卻拿檔名當 source id 去查 —— 每次都查不到，而查不到的處理是「退回中央」，所以不會壞、不會報錯、不會有人發現。

**同一份資料被兩個地方寫，就會有兩個答案。** 播放頭的位置有兩個 handler 在寫：一個用像素（跟著時間軸的 px/s），一個用百分比（整支片的比例）。誰後跑誰贏，於是播放頭會跳。

**只依賴輸入檔的工作，不應該每次重算。** proxy 是原始檔的純函數，卻寫在輸出目錄裡 —— 同一批素材剪第二次，要先把 74 支 4K 重新編碼一遍才能問第一個問題。波形圖也一樣：它按寬度快取，而縮放滑桿每一個 input 事件都用當下滑桿位置算寬度，所以拖一次滑桿就是幾百次 miss、幾百次 ffmpeg 解整支片。

**沒有定義的名字，測不到就會在最貴的時候爆。** 一個下午有三次執行死在這上面，每一次都是搬動 import 或變數造成的，每一次都發生在卡片、定調、選片都付完錢之後 —— 工具花光了所有錢，什麼都沒交出來。全部都能用 pyflakes 在一秒內看出來，現在它跟在測試裡。

**寫死的檔案路徑會腐爛，而且錯的理由會被記成別的。** 字幕字型本來是一份寫死的路徑清單，其中 `/System/Library/Fonts/PingFang.ttc` 在這台機器上根本不存在 —— Apple 把中日韓字型搬到 `/System/Library/AssetsV2` 的隨選資產底下，檔案本身好好的、Pillow 開得起來。原生 App 從來沒發現，因為 Core Text 是用**字型名稱**要字型，不碰路徑；只有伸手去拿路徑的人會拿錯。我第一次的判斷是「FreeType 打不開蘋方」，那是錯的，而且已經寫進註解跟 commit 訊息裡了 —— 症狀對、解法對、理由錯，這種錯最難發現，因為東西已經修好了。

**一個沒人核對過的量測，跟沒有量測一樣。** `zoom_budget` 算「這支素材可以推多近」，用的是「交付 1080×1920」這個假設；而渲染器實際上把每一段縮放到「開頭那個裁切框剛好多少像素」，4K 素材在 9:16 是 1214×2160。所以它准許的最緊裁切（800×1422）報表寫「放大 1.35×」，實際落在更大的畫面上放大 1.52×。**那個唯一決定「可以推多近」的數字，守的是一個根本不存在的輸出**，而且每一份報表裡的 upscale 都錯了同樣的幅度。兩邊各自都「對」，只是沒有人把它們放在一起看過。

**執行層自己回答剪接問題，通常是因為沒有人把事實交給上面那層。** `MAX_UPSCALE` 決定「這顆值不值得放糊」——那是剪接判斷。它會落在那裡，是因為素材清單裡從來沒有寫過「這支推超過 N× 就開始放大」。規劃層看不到那個數字，就只能憑畫面內容說「這裡該推近」，然後在執行層碰壁、記一筆降級。把數字寫進清單之後，選擇權才回到該做選擇的那一層：推到上限、換一支拍得比較緊的、或者不推。

**問模型「你剛剛聽到什麼」，它會順手把那個也改對。** 字幕的 `heard` 欄位存在的唯一理由，是留住辨識器犯的錯 —— 那是判斷校正好不好的唯一證據。但它是跟校正同一次呼叫、同一個 schema 要來的：「辨識器原本給的同一段文字，沒改就填一樣的」。一個被要求修正錯誤的模型，在同一口氣裡引用原文時會把原文也一起修正。實際比對辨識器留在卡片裡的逐字稿，它把 發 寫成了 髮 —— 正好是那句話唯一的錯字，也就是這個欄位唯一該留住的東西。它還會多長出沒人說過的字（句尾多一個「要」、多一個「你」）。辨識器自己的輸出就在硬碟上，直接讀就好；**凡是能從已有資料算出來的事實，都不要跟模型要。**

**時間戳是唯一一種「錯的跟對的長得一模一樣」的答案。** 模型會給每句字幕 `starts_seconds` / `ends_seconds`，那個數字沒有辦法用看的檢查 —— 它永遠是個合理的秒數。辨識器的每字時間是從聲音量出來的，可以檢查。所以現在文字取自模型、時鐘全部取自辨識器：整段校正過的稿子跟整串辨識到的字做一次對齊，每句的頭尾是它自己的字所在的位置，模型的秒數連讀都不讀。對齊到的地方保留實測時間，改掉的地方攤在被取代的那一段裡，漂移 0.000s。

**「這個字是猜的」跟「這個字沒有時間」是兩件事。** 對齊時我把每個字標了 `measured`，然後在算句子頭尾時把沒實測的字濾掉 —— 想擋的是校正加上去的句號（它不佔時間）。但被改過的字也是 `measured=False`，而它佔的是被它取代那個字的真實時間。結果是**每一句被校正過的話，尾巴都被砍掉一個字的長度**，而且完全看不出來。正確的判準是「跨距是不是零」，不是「有沒有實測」。這條是測試抓到的，不是我看出來的。

**回寫發生在伺服器，畫面卻還拿著改之前的數字。** 人編字幕時瀏覽器送出的是那句話原本的時間，伺服器重新對齊之後時間會變 —— 但回應只回了一個筆數。於是資料是對的、畫面是舊的，兩邊都不會報錯。跟「改了結構但沒改指向舊結構的東西」是同一類錯，這次穿的是 HTTP 回應的衣服。

**寬的 `except` 會把「壞掉」偽裝成「沒事做」。** 重新對齊那段本來包在 `except Exception` 裡，退路是「保留原本的時間」—— 那看起來跟正常運作一模一樣。測試裡我用錯了卡片的型別，它就這樣安靜地什麼都沒做，而我差點以為功能是好的。卡片讀不到是正常情況（`OSError` / `ValueError`），型別或名字變了不是。

**模型讀影片用 MM:SS，欄位卻要秒數 —— 這兩種記法在超過一分鐘的素材上會撞在一起。** 素材卡有兩個時間欄位問「這支從第幾秒到第幾秒可用」，而 prompt 從頭到尾沒告訴模型這支多長，schema 還寫著「整支都可用就填總長」—— 要它產出一個沒人給過的數字。庫裡兩支超過一分鐘的素材，兩支都錯了，而且方向相反：71.1 秒那支寫 `usable_to: 110.0`（`1:10` 掉了冒號），113.4 秒那支寫 `1.53`（`1:53` 冒號變成小數點）。**後者才是危險的那個**，因為 1.53 小於片長，所有範圍檢查都放行，然後這張卡片就宣稱一支兩分鐘的素材只有前 1.5 秒能用，而它那筆 action 是 `(1.1, 1.13)`，長 0.03 秒，低於門檻會被靜靜丟掉。整支素材等於消失，沒有任何地方報錯。

**同一個教訓在座標上早就學過了，只是沒有搬到時間上。** 卡片旁邊兩行就寫著「模型會用它自己的 0..1000 座標系回答，不管欄位怎麼說，所以換算在收到的時候做」。時間是一模一樣的問題：它有自己的原生記法，你要的是另一種，那就不要用 prompt 拜託，要在收到的時候處理。現在片長會直接寫進 prompt（秒數跟 MM:SS 都給），收到之後再用量到的片長重讀一次。

**判斷一個數字對不對，要看它跟旁邊的數字湊起來合不合理，不能一個一個看。** `1.1` 跟 `1.13` 單獨看都是合法的秒數，湊成一段就是 0.03 秒的動作 —— 那不是會發生的事。所以起訖是一起評分的，而且兩端必須用同一種讀法（混著讀會得出 `1.1` 到 `73.0` 這種東西）。只有在「一種讀法退化、另一種讀法合理」時才改，剩下的情況保留模型說的：一支 100 秒的素材真的只有 5 秒可用，那是它的判斷，不是錯誤。

**修一個「模型亂給數字」的問題時，要先確認自己拿來當標準答案的那個數字有多準。** 我用本機量到的片長去檢查卡片的秒數，容許值設 0.5 秒 —— 但 Gemini 影片預設 1 FPS 取樣，它能講出來的基本上是整數秒。一支 12.012 秒的素材，它最後看到的一幀在 12，說「動作在 13 秒結束」是取樣造成的進位，不是錯誤。0.5 秒的容許值會把那筆真的動作直接刪掉，**用一個修 bug 的機制製造另一個 bug**。實際可用的空間大得很：MM:SS 撞車最小的情況是剛過一分鐘的素材把 `1:01` 寫成 `101`，超出 40 秒；進位最多 1 秒。1 到 40 之間怎麼選都對，選 0.5 就是沒想過對面那個數字是怎麼來的。

順帶量到的：proxy 比原始檔長約 0.1 秒（重編碼補尾巴），而卡片描述 proxy、EDL 剪原始檔。差距小到不影響剪接，但那是兩個不同的時鐘，值得知道它們不是同一個。

**參數名字寫錯，不會報錯，只會安靜地什麼都不做。** 五個送影片的地方都寫 `"media_resolution": "low"`，而 Interactions API 的欄位叫 `resolution`。SDK 把不認得的鍵原封不動塞進 JSON 送出去，伺服器忽略它 —— 沒有例外、沒有警告、沒有任何跡象。這個旋鈕從第一天起就沒接上任何東西。

它之所以能藏這麼久，是因為**就算接上了也不會有差**：Gemini 3 的影片在 `unspecified`／`low`／`medium` 都是 70 tokens/格，只有 `high` 是 280。所以一個沒生效的設定，跟它生效之後的結果一模一樣。**看不出差別不代表它有在動**，而下次真的需要 `high` 的時候，照舊寫 `media_resolution` 會一樣安靜地失敗。

現在的測試是拿 SDK 的型別去驗，不是比對字串 —— 哪天欄位再改名，會在這裡壞掉，而不是在一次付過錢的呼叫裡。

**解析度的上限在服務端，不在你的檔案裡。** `media_resolution` 是「每格畫面最多用幾個 token」，不是畫質選項。影片一律 1 FPS 取樣、每格壓成 70 個 token，所以送 640×1138 跟送 360×640 得到的是同一份東西。**費用只跟時長有關，跟解析度無關。** 覺得模型看不清楚細節時，該調的是 `resolution` 換 `high`（70 → 280），把 proxy 做大沒有用 —— 那些像素在進模型之前就被丟掉了。

**兩份官方文件對同一個數字說不同的話時，去量。** video-understanding 那頁寫「`low` 是 66 tokens/格，**otherwise 258**」，media-resolution 那頁的 Gemini 3 表寫「`unspecified`／`low`／`medium` 都是 70，`high` 才 280」。差別很要緊：如果是前者，我們那個沒生效的 `media_resolution` 鍵等於讓每一格從 66 變 258，貴了快四倍。實測 gemini-3.6-flash，一支 10 秒的片：不設 667、`low` 667、`medium` 667、`high` 2647。**預設就是最省的那一檔**，所以那個 bug 真的是零成本。前一頁描述的是 Gemini 3 之前的行為，而它沒有說自己在講哪一代。

**同一份文件裡的「最佳做法」值得逐條對一次程式。** 除了 token 數字，那頁還寫了兩條我們都違反的：文字要放在影片**後面**（我們四個地方都相反），以及一個請求只放**一支**影片（定調跟選片一次附 74 支）。第一條免費，改掉了。第二條沒改 —— 拆成 74 次呼叫會貴到不能用，而且實測附上全部影片之後選片明顯變好。**但「知道自己在偏離」跟「不知道」是兩件事**，所以它現在寫在這裡，而不是等下次有人重新發現。

**思考跟答案共用同一個輸出預算，而思考先花。** `max_output_tokens` 不是「答案可以多長」，是「思考加答案總共可以多長」，而模型是先想完才開始寫。所以一個 `thinking_level: high` 的呼叫，實際上是兩個東西在搶同一份配額 —— 輸掉的永遠是答案。實測：預算 48、thinking high，回來的是 `total_thought_tokens: 45`、`total_output_tokens: 0`、`output_text: ''`。

**而預算用完長得不像被截斷，長得像模型拒絕回答。** 沒有半截 JSON 可以認，就是空字串。原本的錯誤訊息是「returned no text」，讀起來像模型出了什麼問題，實際上是我們給的空間不夠。API 自己有講：`interaction.status == 'incomplete'`。**與其從輸出的形狀猜，不如讀它自己說的那個欄位。**

上限改成模型自己的 65536（原本 32768 —— 那還是一種配給，而計費是按產出不是按上限）。

**兩份分別產生的東西要靠順序對應，就是一顆等著爆的雷。** 選片本來是「prompt 裡一整份 74 行的素材清單」加上「後面 74 段影片」，模型要自己認定第 3 行講的是第 3 支。實測 74 支確實對得起來，連清單尾巴都讀得到 —— 但那證明的是「現在沒錯」，不是「不會錯」。清單是 `_describe_material` 產生的，影片是 `_attach_material` 產生的，而後者有一行 `if not item.proxy.exists(): continue`。**只要一支 proxy 沒編出來，影片少一支、清單還是 74 行，從那支之後全部錯開一格** —— 每一顆都配到隔壁的說明，而報表裡的理由寫得頭頭是道。不會報錯，不會失敗，只會產出一支每顆都選錯的片。

改成把每支素材的說明寫在它自己那段影片前面（`review_shots` 本來就是這樣做的）。差別不是「比較好讀」，是**那個假設變成不可能不成立** —— 跳過一支素材，它的說明會跟著一起跳過，因為兩者是同一次迴圈產出的。

順帶一提，驗證這件事的方法是大海撈針：74 支 2 秒的片，其中第 12、41、70 支是彩色其餘全灰，問它哪幾支有顏色。三個全中，包括尾巴那支。這比問模型「你有看到全部嗎」可靠 —— 後者是自我回報，跟 `heard` 欄位同一種毛病。

**運鏡選單上有一個選項，企劃層事前不知道它做不做得到。** `tilt` 需要上下有空間可移，而那要看素材剩多少像素。選單照樣列出來，只在說明裡寫「本機會照實回報做不到」—— 誠實，但是事後誠實：模型挑了、付了錢、渲染完，才在降級欄位看到「a tilt was planned but the crop already fills the frame vertically」。這跟 `push_room` 解決的是同一個問題，而 `push_room` 的註解自己就寫著：「Not told it, it asks for a move nobody can deliver and finds out afterwards, in a degradation.」同一句話對 pan 跟 tilt 一樣成立，只是沒有人把它做出來。

**而我第一版做錯了，錯在把解析度問題當成形狀問題。** 我算「裁切框能不能移動」時假設它一定取滿高 —— 那只在素材沒有多餘像素時才成立。9:16 交付只需要 1920 高，4K 有 2160，**多出來的 240 就是 tilt 的空間**：不放大的情況下有 0.111，把整個 zoom budget 花下去有 0.342。我卻回報 0.000，等於親手把那支素材唯一做得到的運鏡判死。

同一個錯還讓我算錯另一格：我說「交付比例跟素材一樣時兩邊都是 0」。4K 出 FHD 16:9 其實是**橫縱各 0.5** —— 縮一半之後那個框可以放在畫面任何地方。只有 FHD 出 FHD 才真的是 0。

**移動空間跟推近空間來自同一批多餘像素**，裁得越緊能移動的越多。所以回報的是「不用放大就有的空間」，因為一個已經花掉 zoom budget 的數字，企劃層沒辦法拿來跟 `push_room` 一起考慮。

順帶一提，改對之後 `_travel` 也不能再量 proxy 了 —— 形狀問題量 proxy 沒差，解析度問題量 proxy 會說「全世界都不能 tilt」。`_push_room` 的註解早就寫過這一條，我還是又踩了一次。


**推近是唯一會讓框變小的運鏡，所以它是唯一「瞄準錯了會越來越錯」的那個。** `build_zoom_path` 收的是一個固定的中心點 —— 五個取樣位置取平均。主體靜止時完全正確；主體會動時，框在收緊、主體在往外走，兩件事同時發生。實測：主體從畫面 0.35 走到 0.65，開頭貼著左緣（相對位置 0.03），結尾在 1.22 —— **整個跑出畫面**。而且沒有任何降級記錄：`build_crop_path` 會回報「主體其實沒動」，`build_tilt_path` 會回報垂直位移不足，**只有推近從來不問主體有沒有在移動**。

**而需要的資料一直都在手上，只是被丟掉了。** `_sample_frames` 回傳畫格跟它們的時間，推近那條分支寫的是 `frames, _ = ...`。時間就是把五個位置變成一條軌跡的東西 —— 沒有它，能做的只有取平均。

**這件事我一開始歸類成「缺一個組合運鏡」，那是錯的。** 「推近時跟著主體」不是第二種運鏡，是推近本來就該做對的事。差別很重要：如果它是新運鏡，就要加進選單、要模型判斷「這顆主體會不會動」—— 而那是量得出來的，不該拿去問模型。**選單愈短模型選得愈準；能從量測得到的答案，不要變成一個選項。**

**核對用的畫面，不能複述計畫。** 網頁上「原素材＋裁切框」那個疊圖是拿來確認運鏡有沒有真的發生的，而它的標籤印的是 `camera_move` —— 也就是**當初要求什麼**。所以一個退化成定住的橫搖，畫出來是一個不會動的框，上面寫著「橫搖」。旁邊的逐顆驗收明明誠實寫著「畫面保持靜止，並未執行橫搖」，兩邊在同一個畫面上互相矛盾，而錯的那個是唯一被當成證據看的。現在標籤是從 keyframe 反推實際做了什麼，計畫只在兩者不同時附註（「定住（計畫橫搖）」）—— 那個落差才是要看的東西。

**prompt 可以教出一個做不到的組合。** 選片 prompt 在講「主體比畫面寬怎麼辦」時寫「用 `pan` 讓鏡頭橫向讀過去」。模型照做，給一個 `pan` 配一個主體「一排橫向排列的智慧手錶」。但單一主體的 `pan` 是「跟著它走」，而一排錶不會動 —— 執行層照規則退化成定住，記了三筆降級，逐顆驗收判定沒交付。**每一層都做對了自己的事，結果還是錯的，因為源頭教的方法本身不成立。**

真正的做法是 `then_subject`：填起點跟終點，本機量出兩端再連起來。它在 schema 裡有完整說明，**但選片 prompt 的欄位清單從來沒提過它** —— 一個模型讀不到的欄位等於不存在。這跟「執行層做得到什麼要說出口」是同一條，只是這次漏掉的不是能力，是能力的用法。

**一個從第一格移動到最後一格的運鏡，不是那個運鏡，是那個運鏡被剪掉頭尾。** `build_handoff_path` 只產兩個 keyframe：0 秒在 A、結束時在 B。整顆鏡頭都在動，觀眾沒有任何一格靜止畫面可以認出起點是什麼、終點又是什麼。真實剪接的橫搖是**停 → 走 → 停**：先讓眼睛認出 A，走過去，再停下來讓 B 被看見。

**而時間不夠的時候，它不會抗議，它會走到一半停住。** `_limit_speed` 夾住速度之後鏡頭就停在半路 —— 實測 1.2 秒的 calm 橫搖要走 0.700 的距離，只走了 43%，而**終點通常正是這顆鏡頭的重點**。觀眾看到鏡頭開始移動、移動、然後切掉，目的地從未出現。這比「太快看不懂」更糟，太快至少兩端都出現過。現在排不進去會記一筆 `move_does_not_fit_the_time`，帶著需要的速度跟上限。

**「在兩端停下來」該由執行層做，「停多久、總長多少」該由企劃層決定。** 分界線是：停不是風格選擇，是這個運鏡的定義的一部分 —— 跟 smoothstep 緩動同一類，沒有人會去問模型要哪種緩動曲線。而總長取決於「這個 logo 要讀多久」，那要看過畫面才知道，是企劃層的事。**不該給模型的是 keyframe 本身** —— 那等於要它做幾何，跟九宮格猜位置、直接給時間戳、0..1000 座標同一種錯，這個專案已經各踩過一次。

**測試不要把實作細節寫成斷言。** 我一小時前寫了 `assert len(without.keyframes) == 2` 來守「有沒有 track 不影響靜態推近」。一小時後「所有設計過的運鏡都要在兩端停」讓它變成 4 個 keyframe，測試就紅了 —— 而它要守的那個性質根本沒被破壞。斷言該寫「有 track 跟沒 track 產出一樣」，不是「產出兩個 keyframe」。

**選單一直要加新項目，代表缺的是基礎能力不是功能。** 運鏡本來是五個名字加一堆修飾：兩端要停、中途要停、推近要跟著主體。每一個都是為了一件剪輯師本來就會做的事而改程式。在 NLE 裡沒有人等 Adobe 出「停走停」功能，他自己多打兩個 keyframe。**判準是：一個新的剪接想法，需不需要改程式？** 需要就表示你在替剪輯師預先想好每一種可能，然後做成按鈕。

**但基礎能力不等於把 keyframe 交給模型。** 這個專案已經三次把幾何交給它 —— 九宮格位置、時間戳、0..1000 座標 —— 三次都拿回一個看起來很合理的發明。而且真的剪輯師也不打座標：他把框拖到那個東西上面，位置是結果。所以正確的基礎能力是**語意的落點**：一顆鏡頭 = 一串「畫面停在哪裡、停多久」，本機負責量在哪、走多快。一個落點是定住，兩個是移動，兩個指向同一主體但鬆緊不同是推近，三個以上是走停走 —— 五個運鏡名字變成「一串落點碰巧長成的樣子」，事後貼上去的標籤。

**而這個形狀從根本上表達不出矛盾。** 舊 schema 裡「運鏡」跟「主體」是兩個平行欄位，所以 `pan` 配一個靜止主體是合法組合、卻是不可能的指令。落點清單沒有這個問題：一個落點就是畫面要去的一個地方，它跟自己沒有東西可以牴觸。

**改完之後差點釀成災難：** 我把 `camera_move` 從 schema 拿掉，但 `reframe_of` 還在讀它，預設 `"hold"`。下一次跑會**每一顆都定住**，執行層會正確地 dispatch 到一個沒有人送過的名字上，而且不會有任何東西報錯。拿掉一個欄位的時候，要找的不是「誰還在寫它」，是**「誰還在讀它」**。

**用字串定位插入點，等於假設你 grep 到的就是那群的第一個。** 我要把新分支插在「所有運鏡分支之前」，grep 了 `if move in {"push_in"...}`，插在它前面 —— 但雙主體 pan 就在它上面三行。**沒有把分支照順序列出來看過一次**，就動手了。結果新分支被完全遮住，落點重構的主打功能一次都沒跑到。

**而我在註解裡把沒驗證的事寫成了事實。** 那段註解寫「下面比較舊的分支留給單一落點的情況」—— 它描述的是我的意圖，不是現況，而且因為寫得篤定，之後每一次讀到都會被它說服。**註解要寫「為什麼」，不要順手宣告「現在是怎樣」，除非那件事是你剛剛檢查過的。**

**測零件不等於測接線。** `build_look_path` 有七個測試、`_measure_looks` 有三個，全部綠 —— 而呼叫它們的那個分支根本走不到。零件全對，線接錯。這類 bug 只有一種測試抓得到：**從真正的入口進去，斷言那個零件真的被呼叫到。**

**而那個測試我第一版也是錯的。** 我手工建了一個 `Reframe(looks=[...])` 當輸入 —— 但 production 是用 `reframe_of()` 建的，它會順便填 `then_subject`，而 `then_subject` 正是造成遮蔽的那個欄位。所以我把 bug 重新塞回去，測試照樣綠。**假物件的形狀跟真的不一樣，就測不到跟形狀有關的 bug。** 驗證測試會不會失敗的方法，是把 bug 放回去看它紅不紅 —— 這一步做了才發現第一版沒用。

順帶：`Reframe` 的驗證器規定「沒有 subject 就要有 pan_hint 或 intent」，它不認得 `looks`，所以一個只帶三個落點的 reframe 會因為「沒有主體」被擋下來。舊的不變量沒有跟著新的形狀更新。

**只在成功時才存在的報表，是獎盃不是紀錄。** `report.json` 是整條線的最後一個動作，所以渲染之後的任何例外都會把整趟已經決定過、已經付過錢的東西全部丟掉。實際發生過：一次 run 交出了 29 秒的成片、跑完一輪審查、重新規劃了三顆，然後撞到供應商的支出上限死掉 —— 硬碟上有片子，網頁上讀起來像是「這個 run 只產出了一段影片」。而「報表跟影片一樣是交付物」本來就寫在這個專案的原則裡。現在審查迴圈的任何例外都會先寫報表、把錯誤名字記進 `stopped_because`、印出完整 traceback，交付能做的都做完，最後才以失敗結束。

**別人的額度用完，跟自己的額度用完，該做的事一樣。** 供應商的 429 是一個 raw traceback 從 SDK 冒出來，而 `BudgetSpent` 的說明早就寫著正解：「The cap is reached. Deliver what exists; do not degrade to continue.」是誰的上限不改變該怎麼處理。翻譯放在一個地方 —— 九個呼叫點全部改走同一個 `ask()`，跟 `looks_of` 同樣的道理。

要分清楚的是 429 有兩種：**沒錢**跟**太快**。後者 SDK 自己會重試，翻譯成 BudgetSpent 會把一個等一下就好的狀況變成放棄整趟。訊息裡有沒有 spend／billing 是唯一分得出來的線索。

**波形圖的橫軸沒有跟時間軸對齊，那條軌就只是裝飾。** 音樂軌畫的是整首 2 分 35 秒的歌，被攤在 28.9 秒的時間軸上 —— 軌道上任何一點對應到的時間都是錯的，而那條軌存在的唯一理由就是「看聲音落在畫面的哪裡」。裁切邏輯其實寫了，但它讀 `report.json` 的片長，而崩掉的 run 沒有報表。**成片就在硬碟上，量它比問報表可靠。**

**音樂只能從第 0 秒剪一段，而那是最糟的預設。** `atrim=0:{duration}` —— 一支 30 秒的片配一首 2 分半的歌，拿到的永遠是 intro，而 intro 就是寫成還沒有能量的。所以那支片的前 16 秒底下幾乎沒有東西，節奏對得再準也沒用。段落邊界一直都有量（`MusicSectionCandidate`，能量變化偵測），節奏那一階的 prompt 也一直把邊界列給模型看，**它只是沒有任何欄位可以說「用第 3 段」**。又是「量到了、講出來了、但沒有地方可以據此行動」。

**測試素材要讓你想驗的差異撐得過整條處理鏈。** 我用「小聲的 intro」跟「大聲的主段」去驗選段有沒有生效，兩邊量出來都是 -13.1 dB —— 因為鏈尾是 `loudnorm`，它把任何兩個真實訊號拉到同一個響度。換成「真正的靜音」對上「有聲音」才驗得出來，因為正規化補不出無中生有。**驗證用的差異，要選在被測系統不會抹平的那個維度上。**

**「在 brief 裡寫做成 15 秒」跟「這支片就是 15 秒」是兩件事。** 片長本來完全由定調那一階自己決定，使用者唯一能影響它的方式是在 brief 裡用文字請求 —— 而那是一個被跟其他考量一起權衡的意見，不是一個規格。有 `--seconds` 之後它變成「已經決定的事」，而且拿回來還要覆寫，不能相信模型每次都會照抄那個數字。**一個偶爾不照做的欄位，會讓成片安靜地變成另一個長度。**

**音樂也是要剪的東西，不是一段素材。** 一首兩分半的歌配 30 秒的片，只能「從第 0 秒取 30 秒」的話，拿到的永遠是 intro。剪接室的做法有三層：選段落（最重要）、收尾淡出（第二）、抽段接合（手藝，風險最高）。三個都做了之後，分工還是同一條：**哪一段適合這支片是判斷（模型聽得到歌），接點該落在哪裡是量測**（四小節樂句線，或分析器找到的能量邊界）。

**接點一定要交叉淡接，即使落在樂句線上。** 樂句線是音樂的邊界，不是波形的零交越點 —— 硬接照樣會有咔聲。120 毫秒足以蓋掉，又短到兩邊都不會被抹糊。
