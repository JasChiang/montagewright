# fal 傳檔方式與限制

記錄日期：2026-10-01。適用於 `MONTAGEWRIGHT_GEMINI_BACKEND=fal_openrouter`（目前預設）。原生 Google 後端（`MONTAGEWRIGHT_GEMINI_BACKEND=google`）走 File API，不受本文限制。

## 現在怎麼傳

fal／OpenRouter 沒有「上傳一次、之後引用」的檔案機制。`fal_openrouter.py` 的 `_Files.upload` 只回傳本機 `file://` 路徑，真正送出時才把內容以 base64 放進請求本體。

每次呼叫依序：

| 步驟 | 內容 |
|---|---|
| 1 | 讀本機檔案，不上傳到任何儲存空間 |
| 2 | 單檔過大先縮：影片 > 14 MB 重新編碼（`_fal_sized`）；音訊 > 1.5 MB 轉單聲道小 mp3（`_fal_sized_audio`）。依內容 hash 保存，同一檔只縮一次 |
| 3 | base64 放進請求（體積約增加 33%） |
| 4 | 整個請求 > 19.5 MB 時，把這次所有影片按同一比例再縮，最多 3 輪，不丟任何一支 |
| 5 | 仍超過就在送出前報錯，不產生費用 |

重新編碼只改解析度、fps、位元率，時間軸不變；燒在串片上的來源編號與時間碼經實際截圖確認仍可讀。

## 實測上限（2026-09-30，合成影片）

| 情況 | 結果 |
|---|---|
| base64 請求本體 > 20,000,000 bytes | HTTP 413，OpenRouter 未轉送 Google，不計費 |
| 單支影片經 CDN 網址，14 MB | 正確讀取 |
| 單支影片經 CDN 網址，26 MB／70 MB | 400 INVALID_ARGUMENT |
| 兩支 11.4 MB 經 CDN 網址同一請求 | 兩支都正確讀取 |
| 六支 11.4 MB 經 CDN 網址同一請求 | 一次截斷且 usage 為 0，一次 504 |
| agentic，14 MB | 82 秒後 503 high demand |
| agentic，70 MB | HTTP 200、輸入 token 0、答案為空、仍計費 |

因此 fal 上 agentic 一律改送 static；有影片輸入卻回報 0 輸入 token 的回應視為失敗。

## fps：2fps 只影響長影片，而且 fal 本來就只看每秒 1 格

| 檔案 | 原始 | 送 fal 時 |
|---|---|---|
| 一般素材 proxy（約 8–11 秒、30fps、640×360、中位數 0.14 MB） | 30fps | 不動 |
| 多支 proxy 合計超過請求上限 | 30fps | 整批縮小，2 分鐘內的片段用 10fps |
| 剪輯計劃串片（17 分鐘、30fps、28 MB） | 30fps | 2fps、9.3 MB |

**更重要的既有限制：** fal adapter 只轉送 `processing: "static"` 這個模式名稱，不轉送 `fps`。程式對快速運動素材卡要求的 4／8 fps、審片要求的 2 fps，在 fal 上都不會生效，Gemini 實際依預設每秒取 1 格。所以在 fal 上，素材檔是 30fps 或 2fps，模型看到的取樣密度相同。

### 可能的意外

| 狀況 | 說明 |
|---|---|
| 短暫事件消失 | 0.5 秒（2fps）或 1 秒（取樣）以內的瞬間可能落在兩格之間，例如短暫的按鍵亮起、一閃而過的 UI |
| 看不出動作品質 | 搖鏡是否順暢、手持晃動、拉焦過程無法從每秒 1–2 格判斷。運鏡速度與失焦另有本機量測，影響有限 |
| 串片極短片段 | 串片中短於 0.5 秒的選段可能只剩 0–1 格 |
| 素材卡比原生後端粗 | 快速運動素材在原生後端會以 4／8 fps 看，在 fal 上只有每秒 1 格 |

時間軸與聲音不受影響：重新編碼長度誤差 < 0.2 秒，fps 只作用於畫面。

## 尚未處理、可行方向

- 需要細看快速動作時：本機剪出該段並放慢（例如 4 倍）後再送，等效提高取樣；回答中的時間須換算回原時鐘，且仍須遵守「經過模型的時間一律 MM:SS」。
- 或讓少數需要細看、需要 offset、需要 agentic 的呼叫走原生 Google 後端。
- fal CDN 網址：可讓請求本體變小、同檔重複使用，但單支仍約 20 MB 上限；網址取得者即可存取，保存期限未查證。客戶素材是否適合，需使用者判斷。
- 一小時以上的長訪談在 fal 上無法以單一影片送出，需改送文字索引加本機剪出的短片段。
